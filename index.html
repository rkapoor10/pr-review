TLDR

A custom webhook whose payload did not match the trigger's conditions was reported as a red Failed in the trigger's Activity History, and often stayed stuck on “Trigger event was queued” forever. We reclassified the seven condition-mismatch statuses as skips, and routed every path that abandons an event through one write that replaces the queued placeholder row. A user firing a non-matching webhook now sees a Skipped chip with the real reason, and a dropped event shows a real failure instead of a permanent “queued”.

What changed (high level)

Two reported outcomes change on the Activity History screen for custom webhook triggers. An event that was evaluated and simply did not satisfy the configured payload, header, metadata, JEXL, filepath, action, or event conditions is now Skipped rather than Failed, is findable under the Skipped status filter, and no longer counts toward the trigger's activation count or its “last activation” summary. Separately, five code paths that used to stop processing an event without recording anything now record a real terminal outcome, so the row the webhook endpoint creates is no longer left at “queued” as the event's permanent state.

Misconfiguration signals stay Failed on purpose: no enabled trigger found, no matching trigger for repo, event-signature mismatches, and polling events with no versions. A row still sitting at QUEUED also stays Failed, because it means the event was accepted and then never processed. The git-provider webhook path is untouched.

How it was changed

Status classification is decided by exclusion. One shared set lists the skipped statuses, and anything not in that set or the success set falls through to Failed. Adding the seven condition-mismatch statuses to the skipped set therefore fixes the status chip, the status filter, and the “no execution was attempted” flag in one edit.

The orphaned-placeholder fix is a consolidation. Both event processors previously wrote history rows inline at some call sites and skipped it entirely at others, and one path used a plain insert that added a second row next to the placeholder instead of replacing it. Every terminal path in both processors now calls one private method that keys the write to the event's correlation id and upserts. A new shared helper holds the query construction and the fallback that copies request-supplied identifiers onto responses that could not resolve a trigger.

The webhook endpoint's placeholder write changed from an overwriting upsert to an insert-only one. The placeholder is written after the event is handed to the consumer, because the correlation id comes back from that call, so a slow placeholder write could previously land after the processor had already recorded the real outcome and reset the row to queued.

Code implementation details

  • TriggerEventResponse.java — the shared status contract: adds the seven NO_MATCHING_TRIGGER_FOR_* condition-mismatch statuses to SKIPPED_STATUSES, which is read by the status chip, the status filter, the response-level exceptionOccurred flag, and the derived failed set.
  • TriggerEventHistoryHelper.java — new shared utility class: holds the correlation-id query used by every writer of an event's row, a fallback that copies the request's trigger, pipeline, scope, and type onto a response that resolved no trigger, and a builder for outcomes that have no response to map from, such as an exception thrown before any trigger was found.
  • TriggerWebhookEventDetails.java — new interface: lets one helper read either in-flight event entity. The two ingestion paths keep their pending events in different collections but report them through the same history row.
  • TriggerEventHistoryRepositoryCustomImpl.java: adds an insert-only insertIfAbsent built from $setOnInsert, widens the existing upsert to also persist headers, trigger name, polling doc id, build source type, and build, and moves the identifier writes into one method shared by both.
  • NGTriggerWebhookConfigResourceImpl.java: writes the queued placeholder through insertIfAbsent instead of upsert, and marks it as no execution attempted.
  • TriggerCustomWebhookExecutionServiceImpl.java and TriggerWebhookExecutionServiceImpl.java: route the normal, discard, exception-past-retry, and trigger-not-found paths through one recordEventOutcome method, and replace the plain insert in the trigger-not-found branch with that upsert.
  • TriggerEventResponseHelper.java: computes “no execution attempted” from the whole skipped family instead of an exact match on the single SKIPPED status.
  • Tests: pin the intended bucket for all 41 status values so a new status fails until classified, cover the placeholder's insert-only write and its status, cover the duplicate-row repro and the final-attempt exception leak, and cover the skipped family's effect on the activation flag.

Reviewer frame — setup

One custom webhook call produces exactly one Activity History row, and two different components write it. The endpoint NGTriggerWebhookConfigResourceImpl writes a QUEUED placeholder synchronously, and an async processor is meant to replace it with the real outcome. Two processors exist and both are in scope: TriggerCustomWebhookExecutionServiceImpl for the queue-based flow and TriggerWebhookExecutionServiceImpl for the iterator-based one.

The row is addressed by (accountId, eventCorrelationId), and that index is not unique, so a plain insert silently produces a duplicate rather than an error. What the reader sees is computed at read time: TriggerEventStatusHelper.toStatus buckets the stored status into SUCCESS, SKIPPED, or FAILED by checking two sets and defaulting everything else to FAILED. The same two sets build the status filter.

Activity History reads that row two ways, and which one applies depends on an account setting. NGTriggerEventServiceImpl.formTriggerEventsCriteria filters on parentUniqueId when parent-id querying is enabled, and otherwise filters on accountId, orgIdentifier, and projectIdentifier by equality. This matters for every write in the diff.

Affected path

webhook POST → enqueue returns correlation id → QUEUED placeholder row written → processor picks event up → outcome upserted over the same row → Activity History reads the row → status bucketed at read time

The branches the patch changes are: the processor stops on a discard, the processor stops on an exception it will not retry, the processor resolves no trigger, and the placeholder write races the outcome write.

What must remain true

  • Every write to an event's history row must select it by both accountId and eventCorrelationId, or a second row appears instead of the placeholder being replaced.
  • A path that stops processing an event permanently must leave a terminal status behind, because the placeholder is otherwise the event's final reported state.
  • The placeholder write must never overwrite a status the processor already recorded.
  • A row must keep values for every field the Activity History query filters on by equality, or the event stops appearing under its own trigger. That set is parentUniqueId, or accountId plus orgIdentifier plus projectIdentifier, plus targetIdentifier and triggerIdentifier.
  • A status not listed in either the success or the skipped set renders as a red failure, so every enum value needs a deliberate bucket.

Decisions the author owns

Stated decision — where the skipped boundary sits

The description draws the line at “evaluated and did not match” versus “misconfigured, so act on it.” That is why NO_ENABLED_TRIGGER_FOR_*, NO_MATCHING_TRIGGER_FOR_REPO, NO_MATCHING_TRIGGER_FOR_FOR_EVENT_SIGNATURES, and POLLING_EVENT_WITH_NO_VERSIONS stay Failed. The obligation this creates is a product one: Skipped events also drop out of the activation count and the “last activation” summary, so a trigger that only ever receives non-matching webhooks will now read as never activated. That is the intent, but it is a visible change to an existing number.

Stated decision — QUEUED stays Failed

Reasonable, and tested. One consequence is worth confirming: the placeholder now also writes executionNotAttempted: true, and TriggerFilterHelper.createCriteriaForTriggerEventCountLastNDays excludes rows where that flag is true. So a genuinely dropped event now renders as Failed while being excluded from the activation count, where before it was counted. Defensible, but it is a second unstated change to the same number.

Implemented decision — rationale needed: which fields the backfill covers

prepareForRecording restores triggerIdentifier, targetIdentifier, parentUniqueId, and ngTriggerType from the request, but not orgIdentifier or projectIdentifier. Those last two are also filtered on by equality on the non-parent-id read path, and the response carries null for both when no trigger was resolved. What is the reason for stopping at four fields rather than covering the whole equality-filtered set?

Implemented decision — one row per event when several triggers match

recordEventOutcome is called once per response inside responseList.forEach, and every call targets the same (accountId, eventCorrelationId) row. With more than one matched trigger, only the last response survives. This predates the patch, but centralizing the write makes it a property of the new design rather than an accident of two call sites. Is one row per webhook call the intended contract, or should a multi-trigger match produce one row per trigger?

Assumptions to verify
